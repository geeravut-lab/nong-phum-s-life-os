# ประเมินราคา Premium / Family / PAYG เทียบต้นทุนจริง

ตรวจ 2026-09-26 · ราคาที่ประเมิน: **Premium ฿89/เดือน (฿890/ปี) · Family ฿149/เดือน (฿1,490/ปี) · PAYG 50 สตางค์/ครั้ง**
โควต้าฟรี/เดือน: แชท 40 · เอกสาร 12 · ตัดสินใจ 8 · เสียง 15 · **รวมไม่เกิน 60 ครั้ง**

> **ข้อควรรู้ก่อนอ่าน:** ระบบ **ไม่ได้บันทึกจำนวน token ของการเรียกใด ๆ เลย** — `ai_usage_monthly`
> นับเป็น "ครั้ง" ล้วน ๆ ตัวเลขต้นทุนข้างล่างจึงเป็น **การประมาณจากขนาด prompt ในโค้ด**
> ไม่ใช่ตัวเลขจากบิลจริง ดูข้อ 6 ("สิ่งที่ควรทำก่อนตัดสินใจขึ้นราคา")

สมมติฐาน: 1 USD = **฿33.3** (อัตรา ก.ย. 2026) · ขนาดต่อครั้งประมาณจาก `phum.server.ts`
(แชท 4,000 in / 500 out · เอกสาร 6,000 / 800 (PDF 1–3 หน้า) · ตัดสินใจ 4,000 / 1,200 · เสียง 2,000 / 200 ≈ เสียง 60 วินาที)

## 2. ผู้ใช้ฟรี 1 คนที่ใช้เต็มโควต้า ต้นทุนเท่าไร

เพราะเพดานรวมคือ 60 ครั้ง ส่วนผสมที่ **แพงที่สุด** ที่ยังอยู่ในโควต้าคือ เอกสาร 12 + ตัดสินใจ 8 + แชท 40

| ถ้า default เป็น   | ต้นทุนผู้ใช้ฟรี 1 คน/เดือน (ใช้เต็ม) |
| ------------------ | ------------------------------------ |
| anthropic (ตอนนี้) | **≈ ฿27**                            |
| gemini             | **≈ ฿11** (≈ ฿23 หลัง ม.ค. 2027)     |

แปลว่า **Premium 1 คน (฿89) เลี้ยงผู้ใช้ฟรีที่ใช้เต็มได้ราว 3 คน** ตาม default ปัจจุบัน (หรือ ~8 คนถ้าใช้ Gemini)
— ยังไม่รวมค่า infra ข้อ 4

## 3. ปัญหาที่ใหญ่ที่สุด: Premium = ไม่จำกัด และไม่ถูกนับ

`checkAndConsumeAiQuota` (billing.functions.ts:232) คืน `allowed: true` ทันทีถ้าเป็น premium/family
**ไม่แตะตัวนับเลย** ผลคือสองอย่าง:

1. **Premium ใช้ AI ได้ไม่จำกัด** ที่ ฿89/เดือน จุดคุ้มทุน (ยังไม่คิด infra):
   - ตัดสินใจ **67 ครั้ง/เดือน** · เอกสาร **135 ครั้ง** · แชท **424 ครั้ง**
   - ผู้ใช้ที่กด "ตัดสินใจ" วันละ 10 ครั้ง = 300 ครั้ง/เดือน → ต้นทุน **฿396** จากรายได้ ฿89 → **ขาดทุน ฿307/คน/เดือน**
   - รายปี ฿890 คือความเสี่ยงก้อนเดียวที่ใหญ่สุด: ขายไม่จำกัด 1 ปี ในราคาเท่ากับ Opus 67 ครั้ง
2. **ไม่มีข้อมูลว่าคน Premium ใช้เท่าไร** เพราะไม่ได้นับ → วันนี้ตอบไม่ได้เลยว่า ฿89 พอหรือไม่พอ **ด้วยข้อมูลจริง**

**คำแนะนำ:** นับทุกคน (รวม premium) แต่ **บังคับ** เฉพาะผู้ใช้ฟรี แล้วใส่ fair-use cap ให้ Premium
เช่น 500 ครั้ง/เดือน (ต้นทุนแย่สุด ≈ ฿110 ที่ default ปัจจุบัน, ≈ ฿55 ถ้าใช้ Gemini) เกินแล้วค่อยลดความเร็ว
หรือคิด PAYG — ไม่ใช่ตัดบริการ

## 5. LINE OA เป็นเพดานที่มองข้ามง่าย

`line_monthly_cap` default = **300 ข้อความ/เดือน ทั้งระบบ** (ไม่ใช่ต่อคน) — `line-deliver.server.ts:50`
ที่ผู้ใช้ 100 คน = **3 ข้อความ/คน/เดือน** ซึ่งไม่พอสำหรับ digest รายวันแม้แต่คนเดียว

- digest รายวัน 1 คน = ~30 ข้อความ/เดือน → เพดาน 300 รองรับได้ **10 คน**
- ข้อความแบบ **reply** (ตอบภายในหน้าต่างหลังผู้ใช้พิมพ์มา) LINE **ไม่คิดเงิน** ส่วน **push ถูกคิด** —
  ถ้าดันงานแจ้งเตือนไปทาง reply ให้ได้มากที่สุดจะประหยัดจริง **(ต้องยืนยันเงื่อนไขกับ LINE ก่อน)**
- **ควรทำให้ cap เป็นต่อผู้ใช้ ไม่ใช่ต่อระบบ** และผูกจำนวน digest เข้ากับแพ็ก (ฟรี = สัปดาห์ละครั้ง, Premium = รายวัน)
  นี่เป็นเหตุผลขายของที่จับต้องได้มากกว่า "AI ไม่จำกัด" และต้นทุนคาดเดาได้

## 6. สิ่งที่ควรทำก่อนตัดสินใจขึ้น/ลดราคา

เรียงตามผลต่อกำไรต่อแรงที่ลง:

1. **บันทึก token ทุกครั้งที่เรียก** (provider, model, in, out, task) — ตอนนี้ทุกตัวเลขในเอกสารนี้เป็นการประมาณ
   ข้อนี้ทำครั้งเดียวแล้วเปลี่ยนการตั้งราคาจากการเดาเป็นการวัด
2. **ย้าย `reasoning` ออกจาก Opus 5** — ลดต้นทุน "ตัดสินใจ" จาก ฿1.32 เหลือ ฿0.53 (Sonnet 5) หรือ ฿0.25 (Gemini Flash)
   ทันทีโดยไม่ต้องแตะราคาขาย นี่คือจุดที่เงินรั่วมากที่สุดต่อ 1 ครั้ง
3. **นับการใช้งานของ Premium** (บังคับเฉพาะฟรี) + fair-use cap ตามข้อ 3
4. **แก้ราคา PAYG ให้ต่างตามงาน** — 50 สตางค์ขาดทุนบนงานที่คนยอมจ่ายจริง:

   | งาน      | ต้นทุน | PAYG ฿0.5 | ผล        | เสนอ |
   | -------- | ------ | --------- | --------- | ---- |
   | แชท      | ฿0.21  | ฿0.5      | +฿0.29 ✅ | ฿0.5 |
   | เสียง    | ฿0.08  | ฿0.5      | +฿0.42 ✅ | ฿0.5 |
   | เอกสาร   | ฿0.66  | ฿0.5      | −฿0.16 ❌ | ฿2   |
   | ตัดสินใจ | ฿1.32  | ฿0.5      | −฿0.82 ❌ | ฿3   |

   (ถ้าย้ายไป Gemini ทั้งหมด ฿1 เหมาทุกงานก็มีกำไรทุกช่อง)
   หมายเหตุ: `paygEnabled` default = **false** → วันนี้ผู้ใช้เกินโควต้าถูก **บล็อก** ไม่ได้สร้างรายได้เลย

5. **Family ฿149 ยังไม่ได้ให้อะไรเกิน Premium** — ดูข้อ 7 นี่เป็นบั๊ก ไม่ใช่เรื่องราคา

## 7. บั๊กที่ทำให้ Family ฿149 ขายไม่ได้ในทางปฏิบัติ

ตอนยืนยันการชำระเงิน (`billing.functions.ts:519`) ระบบ set `plan_tier` ให้ **คนจ่ายคนเดียว**
สมาชิกครอบครัวคนอื่นยังเป็น `free` และยังติดโควต้า 60 ครั้งเหมือนเดิม
`isPremiumActive` ก็ดูแค่ `profiles.plan_tier` ของตัวเอง ไม่ได้ดูว่าอยู่ในครอบครัวที่จ่าย Family ไว้หรือไม่

**แปลว่า ฿149 วันนี้ = ฿89 แบบจ่ายแพงขึ้น ฿60** ต้องเลือกทางใดทางหนึ่ง:

- ให้สิทธิ์ทั้งครอบครัว: `isPremiumActive` เช็กต่อว่าเจ้าของครอบครัวมี `plan_tier = 'family'` อยู่หรือไม่
  (ทำที่จุดเดียว ดีกว่าไปเขียน `plan_tier` ใส่ทุกคนซึ่งจะค้างเมื่อหมดอายุหรือมีคนออก) + **จำกัดจำนวนที่นั่ง เช่น 5 คน**
- หรือ **หยุดขาย Family** จนกว่าจะทำข้อบน

ถ้าให้สิทธิ์ 5 คนจริง: ฿149 ÷ 5 = **฿29.8/คน** ซึ่ง **ต่ำกว่า** ต้นทุนผู้ใช้ที่ใช้เต็ม (฿27) แบบเฉียดฉิว
→ ถ้ายังใช้ default anthropic อยู่ Family คือแพ็กที่ขาดทุนตั้งแต่ตั้งราคา
ควรเป็น **฿199–249 สำหรับ 5 คน** หรือ ฿149 สำหรับ **3 คน** (= ฿49.7/คน)

## 8. สรุปว่าราคาที่ตั้งไว้เหมาะหรือไม่

| ราคา                  | ความเห็น                                                                                                                                                              |
| --------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Premium ฿89/เดือน** | **ระดับราคาเหมาะกับตลาดไทย** (Netflix มือถือ ฿99 · YouTube Premium ฿179) — ปัญหาไม่ใช่ตัวเลข แต่เป็นคำว่า "ไม่จำกัด" ที่อยู่ข้างหลัง ใส่ fair-use cap แล้ว ฿89 ใช้ได้ |
| **฿890/ปี**           | ส่วนลด 16.7% = ฟรี 2 เดือน มาตรฐาน แต่ **ห้ามขายคู่กับ "ไม่จำกัด"** ก่อนแก้ข้อ 3                                                                                      |
| **Family ฿149**       | **ยังไม่ควรขายตามสภาพโค้ดตอนนี้** (ข้อ 7) ถ้าแก้แล้วให้ 5 ที่นั่ง ควรขึ้นเป็น ฿199–249                                                                                |
| **PAYG ฿0.5/ครั้ง**   | **ต่ำกว่าทุนบนเอกสารและการตัดสินใจ** ต้องแยกราคาตามงาน (ข้อ 6.4)                                                                                                      |

**ลำดับที่แนะนำ:** ข้อ 6.2 (ย้าย reasoning ออกจาก Opus) → 6.1 (นับ token) → 6.3 (นับ+cap ของ Premium) → 7 (Family) → 6.4 (PAYG)
สองข้อแรกลดต้นทุนได้ทันทีโดยไม่ต้องแตะราคาที่ประกาศไปแล้ว
